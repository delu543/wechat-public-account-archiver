# 可重复的缓存增量与 Word 交付

## 现在能自动化到哪一步

推荐入口为 `main.py cache-update`。它复用已验证的共享公开缓存读取器，不控制微信界面、不读取聊天库、不获取或重放客户端签名、不请求微信网络接口。

- 已保存数据：自动核对订阅、精确账号身份、旧正文片段、已交付 Word 收据、重复链接与正文；按号生成带时间的“已发现增量”。
- 新列表还没写入缓存：程序不能凭旧文章链接推导所有新文章。此时需要正常人工浏览**缺少数据的号**，收集器应先启动，再从最新往下加载；不需逐篇打开，也不应无差别要求重新刷新全部账号。
- 浏览建议到“最近已导出日期”为止；这只是避免重复工作的提示。旧片段、恢复区间和未知完整覆盖继续单列，不因该日期向前推进而关闭。
- 全历史仍需要可验证的完整分页目录或足够的实际缓存。没有这样的来源时，不承诺一次点开文章就能取得全部历史，也不要求用户无休止翻页代替一个未验证的接口。

推送库 `weekly-run` 是另一条条件路线：已授权且绑定、HMAC、库新鲜度均通过后可以不依赖每周浏览；在当前机器上，这一真机初始化链路尚未验收成功。推送也可能遗漏“发表未群发”。它不是缓存不足时的自动兜底。微信读书缺少短内容，不是所有内容的替代来源。

## 固定操作

在实际产品工作区运行；发布用的源码仓库不是产品数据库。`--until YYYY-MM-DD` 可固定本次截止日期，省略时取本机当天；内容日期按北京时间核对。

```sh
# 默认/--check：只读现有暂存、产品节点和交付收据，不读取当前微信缓存，不写库
.venv/bin/python main.py cache-update --check

# 数据已保存时：按号导出已有合格正文，明确接受未知完整覆盖
.venv/bin/python main.py cache-update --export --accept-discovered

# 缺少当前数据时：先启动有限收集，再由用户正常浏览所需主页
.venv/bin/python main.py cache-update --collect --seconds 1
# 先试读一次当前公开缓存并复查；已有所需数据时跳过人工浏览
# 确需人工加载时才开启持续累计：
.venv/bin/python main.py cache-update --collect --seconds 600

# 收集后立即准备 Word；只有本次独立收集已获准时才加暂停例外
.venv/bin/python main.py cache-update --collect --seconds 600 --export --accept-discovered --allow-local-stage-while-paused
```

`--account-biz` 可重复，限定已注册的精确账号；`--exclude-biz` 可重复。配置中排除的账号不会因本次“所有”而偷偷恢复，显式冲突会报错。新账号先用已授权公开文章解析流程登记其精确身份和用户要求的起点，不得拿同名搜索结果直接建归档。

暂停例外只允许本次有限公开缓存暂存，不更改后台开关；运行中暂停值或更新时间变化就停止提交。无例外时暂停会在来源读取/创建暂存之前阻挡。单纯整理已保存内容不运行抓取。收集上限30分钟、2–30秒间隔，每轮所有账号共用一次快照；Ctrl+C保留断点。

## 本机配置（不提交真实路径和节点）

```yaml
cache_update:
  excluded_biz: []
  prior_stage_roots: []
  delivery_receipts: []
  # stage_root: "/absolute/path/to/owned-public-stages"
```

通常不需设置 stage_root，默认 `<output>/cache-updates/stages`。迁移旧任务时，只把已经核对的自有公开 stage 目录放入 `prior_stage_roots`，将已验收的 `delivery-manifest.json` 放入 `delivery_receipts`。不能指向微信数据库或任意聊天库。

每次自动选择同账号、同起点、截止不晚于本次的最新累计批次。检查旧批次是只读；收集时继承到本次新日期文件，保留原窗口身份与旧文件。范围或已归档基线变化导致不兼容时，应重新核对，不强行混并。

`passive_weekly.delivered_baseline_max_article_id` 为此前已交付文章的冻结节点；不得用本次抓取后的最大 ID 重算。`recovery_gaps` 和 `incomplete_article_ids` 保留未解决范围/片段。没有历史交付证据时，不任意把全部现有文章算成已交付。

## 交付收据与恢复

输出目录：`<output>/cache-updates/deliveries/batch-日期-指纹/`。

目录含按号 Word、冻结 `plan.json` 和 `delivery-manifest.json` 汇总（包括未生成文档的账号和缺口）。正文保留短内容、原样文字和永久链接；无正文不生成空文档。文档标题、正文、链接、成员及哈希先由程序核对，状态为 `awaiting_render_review`，不是已交付。

交付者（可为 Codex）按文档 Skill 生成预览并检查排版、正文和缺字后登记：

```sh
.venv/bin/python main.py cache-update --confirm-delivery '<本入口返回的完整批次目录>' --render-reviewed
```

这个参数是**实际完成渲染检查的声明**，不是自动渲染命令；不能为了让去重生效而跳过检查。无需额外要求用户手点确认。检查通过生成独立 `verification.json`，下一轮自动使用该收据去重。已有八号交付可直接读其已核验收据，无需重做 Word。

收据、Word 哈希、精确 biz、永久链接和成员日期必须一致；篡改/缺失停止使用该收据，不把文章误标完成。已交付 URL 出现不同正文保留为版本缺口，不覆盖旧 Word。相同正文的另一链接不重复导出。

中断后优先续接同一冻结批次，新发现内容留给下一批；已存在 Word 必须逐文匹配后才可复用，损坏文件保留且报错，不覆盖。新批次不写产品正文、`last_success` 或完整覆盖节点。多写入者由独立输出锁互斥。

## 验收层次与回退

合成回归覆盖暂停、跨日只读继承、交付成员去重、版本变化、短正文、链接脱敏、中断续跑、成员核验和零空文档。真实只读验收核对既有八号117篇收据，重复候选为0，仍保留历史缺口；不等于测试了下一周的新缓存或完整发表覆盖。

本次没有部署或启动菜单栏 App、LaunchAgent，也没有解除暂停。要切换定时/按钮，须另外验收安装副本、暂停按钮、真实新批次和提示打开的目录，不能把代码已推送当作插件已全自动。

回退只需停止使用新入口，保留新暂存/收据；旧产品库、已交付文档、完整导出器均未替换。当前模块复用项目自身读取器、Word工具及已有依赖，没有引入外部爬虫、第三方下载代理或新密钥来源。
